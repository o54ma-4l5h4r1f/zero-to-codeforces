Do not change code and hope. Look at the verdict, follow a checklist in order, and test your code against a slow, simple solution.

Before this lesson

  • You know the verdicts WA, TLE and RE → How Codeforces works
  • You can count the steps of a loop → How much does my code cost?
  • You know when to use long long → int or long long?

First: the verdict tells you where to look

Each verdict has its own checklist. Start with check 1. Do not jump to check 2 before you finish check 1.

VerdictCheck these, in this order
Wrong answer (WA)
  1. Read the statement and the output format again, slowly.
  2. Test edge cases by hand: \( n = 1 \), all equal, the biggest values.
  3. Overflow: can a sum or a product pass \( 2 \cdot 10^9 \)?
Time limit exceeded (TLE)
  1. Count the steps for the biggest \( n \). More than about \( 10^8 \)? You need a new idea.
  2. A loop that never ends: does the loop variable really change?
  3. endl or no fast-input lines: print "\n", keep the template.
Runtime error (RE)
  1. An index out of range: a[n], a[-1], an array too small.
  2. Division by zero: x / 0 and x % 0 both crash.
  3. An empty container: v.back() when v is empty.
Memory limit exceeded (MLE)
  1. The size of your arrays: \( 10^8 \) int values need 400 MB. The usual limit is 256 MB.
  2. A 2D array of \( n \cdot n \) cells: with \( n = 10^4 \) that is \( 10^8 \) cells.
  3. A vector that grows forever in a loop that never ends.

Wrong answer still? Then check uninitialised variables (int sum; holds garbage) , resets between test cases, and spelling: YES or Yes.

The strongest trick: stress testing

All samples pass, but the judge says Wrong answer on test 7. You cannot see test 7. So you make your own tests. This is stress testing.

1 · Story — two students

One student is fast but makes mistakes. The other is very slow but always right. Give both the same small questions. When their answers differ, you found a question where the fast student is wrong.

2 · Picture — the three parts

PartWhat it is
fast(...)Your real solution. Maybe it has a bug.
slow(...)A brute force: simple loops that are surely correct. Speed does not matter.
generatorMakes small random inputs: \( n \le 6 \), values from −5 to 5.

Small inputs are the point. A wrong case with 4 numbers is quick to check by hand. A wrong case with 1000 numbers is useless.

3 · Code — everything in one file

Toy task: find the biggest sum of a subarray, a block of neighbours with at least one element.


#include <bits/stdc++.h>
using namespace std;

long long fast(const vector<int> &a) {     // the solution you want to submit: n steps
    long long best = a[0], cur = 0;
    for (int x : a) {
        cur = max(cur + x, (long long)x);  // continue the old subarray, or start at x
        best = max(best, cur);
    }
    return best;
}

long long slow(const vector<int> &a) {     // every subarray: n * n steps, surely right
    int n = a.size();
    long long best = a[0];
    for (int i = 0; i < n; i++) {
        long long sum = 0;
        for (int j = i; j < n; j++) {
            sum += a[j];                   // sum of a[i..j]
            best = max(best, sum);
        }
    }
    return best;
}

int main() {
    mt19937 rng(12345);                    // random generator; same tests on every run
    for (int test = 1; test <= 1000; test++) {
        int n = rng() % 6 + 1;             // n from 1 to 6
        vector<int> a(n);
        for (int &x : a) x = (int)(rng() % 11) - 5;   // values from -5 to 5
        long long f = fast(a), s = slow(a);
        if (f != s) {                      // the first input where they differ
            cout << "DIFFERENT on test " << test << "\n" << n << "\n";
            for (int x : a) cout << x << " ";
            cout << "\nfast = " << f << ", slow = " << s << "\n";
            return 0;
        }
    }
    cout << "all 1000 tests are equal\n";
}

Try it: change best = a[0] in fast to best = 0. Now the program prints a small array of only negative numbers. That is the bug: the answer cannot be an empty subarray.

You do not need to understand how fast works. Only the idea matters: compare it with slow.

Solve one together

Problem. There are \( t \) test cases. Each one has \( n \) numbers. Print how many of them are even. This code passes the first test case but fails the second. Find the bug.

  1. The code. Read it once before you trace it. 
    
int t; cin >> t;
int cnt = 0;
while (t--) {
    int n; cin >> n;
    for (int i = 0; i < n; i++) {
        int x; cin >> x;
        if (x % 2 == 0) cnt++;
    }
    cout << cnt << "\n";
}
  2. What is wrong? The verdict is Wrong answer. So we start with check 1: the statement. It is clear: count the even numbers of each test case.
  3. A small test by hand. Input: 2, then 3 and 2 4 5, then 1 and 6. The right output is 2 then 1.
  4. Trace it. We follow the code line by line and write every value in a trace table.
    TestxEven?cnt afterPrinted
    12yes1
    14yes2
    15no22 (right)
    26yes33 (should be 1)
  5. The bug. The counter cnt does not go back to 0 when test case 2 starts. It starts from 2, not from 0.
  6. The fix. Move int cnt = 0; inside the while loop. Or put the work in solve(), as the template does. Run the hand test again: it prints 2 then 1.

#include <bits/stdc++.h>
using namespace std;

int main() {
    int t;
    cin >> t;
    while (t--) {
        int cnt = 0;                     // fresh for every test case
        int n;
        cin >> n;
        for (int i = 0; i < n; i++) {
            int x;
            cin >> x;
            if (x % 2 == 0) cnt++;
        }
        cout << cnt << "\n";
    }
}

Print what your program thinks

A trace table by hand is slow for big loops. Let the program print it. Use cerr, not cout. The judge ignores cerr, so a forgotten line does not give Wrong answer.


for (int i = 0; i < n; i++) {
    sum += a[i];
    cerr << "i=" << i << " sum=" << sum << "\n";   // debug line
}

Still delete these lines before you submit. Printing a lot to cerr takes time.

Wrong ideas people get

  • You may think: All samples pass, so the judge must be wrong.

    The truth: The samples are easy on purpose. The bug is almost always in your code, in a case you did not try.

  • You may think: I will change one line and submit again to see what happens.

    The truth: Each wrong submit costs points. First find an input that fails, then fix the code.

  • You may think: Time limit exceeded means the code needs small speed-ups.

    The truth: Usually you need a faster idea, not a faster keyboard. Count the steps first. See Limits → speed.

Common mistakes

  • You test only the samples. Make your own small tests: \( n = 1 \), all equal, negative numbers.
  • In a stress test you copy the same wrong idea into slow. Write slow in a different, simpler way.
  • Your random tests are big. Keep \( n \) small and the values small, so equal and negative numbers appear often.

Check yourself

  1. You get Runtime error. What do you check first?
    Answer

    An index out of range: a[n], a[-1] or an array that is too small. Then division by zero.

  2. Test case 1 is right, test case 2 is wrong. Alone, test case 2 is right. What is the likely bug?
    Answer

    A variable is not reset between test cases. It keeps its value from test case 1.

  3. Why do we use very small random tests in a stress test?
    Answer

    So we can check a failing case by hand. Small values also make equal and negative numbers appear often.
