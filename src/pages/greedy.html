At every step take the choice that looks best right now, and never go back. Very often this means: sort, then take.

Before this lesson

  • You can sort by your own rule, and you know how pairs sort → Sorting
  • You can write a slow "try everything" solution → Brute force
  • You can compare a fast solution with a slow one (stress test) → How to find your bug

Spot it

  • The statement asks for the minimum or maximum number of something: coins, moves, items.
  • You build the answer step by step. One choice looks clearly best: the biggest, the smallest, the one that ends first.
  • \( n \) is big, like \( 2 \cdot 10^5 \). You cannot try all possibilities, so a sort and one loop must be enough.

Three ways to understand it

1 · Story — one hour of homework

You have 60 minutes. Your tasks need 30, 10, 25 and 20 minutes. You want to finish as many tasks as you can.

Do the shortest task first: 10, then 20, then 25. That is 55 minutes and 3 tasks. A short task never hurts: it leaves the most time for the others. This is a greedy rule: "smallest first".

2 · Picture — one room, many meetings

One room. Each meeting has a start and an end time. A meeting may start at the moment the last one ends. Hold as many meetings as you can.

The rule: among the meetings that still fit, take the one that ends first. So sort the meetings by end time, then walk through them once.

3 · Code — sort by end, then take

Store each meeting as a pair {end, start}. Pairs sort by .first, so the sort puts the earliest end first.


#include <bits/stdc++.h>
using namespace std;

int main() {
    int n;
    cin >> n;
    vector<pair<int,int>> m(n);              // {end, start}
    for (int i = 0; i < n; i++) {
        int s, e;
        cin >> s >> e;
        m[i] = {e, s};
    }
    sort(m.begin(), m.end());                // earliest end first
    int lastEnd = 0, taken = 0;              // all times are >= 0
    for (int i = 0; i < n; i++) {
        if (m[i].second >= lastEnd) {        // it starts after the last taken one ends
            taken++;
            lastEnd = m[i].first;
        }
    }
    cout << taken << "\n";
}

Change it to fit

Most greedy solutions are "sort, then take" with a small change. The DEFAULT: sort small → big, then take from the front.

The problem changes like this……you change this
Sort by a different key. Meetings: earliest end. Homework: shortest task.What you put in .first: m[i] = {e, s}; or t[i] = {len, i};
Take from the other end. "Fewest items whose sum is more than X" (like Twins below): the biggest item helps most.sort(a.rbegin(), a.rend());
Take while possible. You have \( k \) coins of money. Buy as many items as you can.Sort small → big, then while (i < n && a[i] <= k) { k -= a[i]; i++; }

How to trust a greedy

  1. Small cases by hand. Solve 3–5 tiny inputs on paper. Does your rule give the best answer each time?
  2. Try to break it. Look for a counterexample: ties, one huge item, very small numbers. One is enough to kill the idea.
  3. Let the computer try. Write a brute force. Compare both on many small random inputs: a stress test, as in How to find your bug.
  4. The swap idea. Take any best answer. Put your greedy choice in place of its first choice. If it never gets worse, your rule is right. Homework with numbers: tasks of 30 and 10 minutes. Order 30, 10 finishes them at minutes 30 and 40. Swap to 10, 30: they finish at 10 and 40. The last one ends at the same time, and the first ends earlier. So short-first is never worse. Meetings: the meeting that ends first ends no later than any other, so the rest still fits.

When to stop. A choice now changes which choices are good later, and every rule you try breaks? Stop trying greedy rules. This problem probably needs a different tool. The coins 1, 3, 4 are such a problem.

Solve one together

Problem (160A, Twins). There are \( n \) coins with values \( a_1, \dots, a_n \). Take the fewest coins so that your sum is strictly more than the sum of the coins you leave. Limits: \( 1 \le n \le 100 \) and \( 1 \le a_i \le 100 \).

  1. What is asked? The smallest number of coins with mine > total - mine.
  2. A small example by hand. Coins 3 1 2 5 4, so the total is 15. Sort big → small: 5 4 3 2 1.
    take543
    mine5912
    the rest1063
    mine > rest?noyesyes

    The answer is 2 coins.

  3. The idea. This is "take from the other end". A big coin adds the most to my sum and takes the most from the rest. So take the biggest first. Swap idea: if a best answer uses a smaller coin, swap it for a bigger one. Its sum only grows.
  4. Why is it fast enough? Sort is \( O(n \log n) \), then one loop. For \( n = 100 \) this is tiny.

#include <bits/stdc++.h>
using namespace std;

int main() {
    int n;
    cin >> n;
    vector<int> a(n);
    int total = 0;
    for (int i = 0; i < n; i++) {
        cin >> a[i];
        total += a[i];
    }
    sort(a.rbegin(), a.rend());                 // big -> small: biggest coin first
    int mine = 0, taken = 0;
    for (int i = 0; i < n; i++) {
        if (mine > total - mine) break;         // I already have strictly more
        mine += a[i];                           // take the biggest coin that is left
        taken++;
    }
    cout << taken << "\n";
}

Speed: \( O(n \log n) \) for the sort, then \( O(n) \) for one loop. Fast enough for \( n = 2 \cdot 10^5 \).

Wrong ideas people get

  • You may think: My greedy rule passes the samples, so it is correct.

    The truth: The samples rarely hold the counterexample. Test the rule with the four steps above.

  • You may think: Taking the biggest coin first always gives the fewest coins.

    The truth: Only for some sets of coins. With 1, 3, 4 it fails.

  • You may think: Sorting the meetings by start is as good as by end.

    The truth: A long meeting that starts early can block many others, like G in the picture.

Common mistakes

  • You forget to sort, or you sort in the wrong direction.
  • More or at least? In 160A the sum must be strictly more. > and >= give different answers.
  • The sum of many numbers is in an int. Use long long when it can pass \( 2 \cdot 10^9 \).

Not now

  • Problems where every greedy rule breaks, like the fewest coins of 1, 3, 4. They need a table of small answers. You learn it in Dynamic programming.
  • A best choice that changes after every step, like "always take the smallest of what is left" while new items arrive. That needs a container that gives the smallest fast: a priority queue, in Shortest path (Dijkstra).

Check yourself

  1. Coins 1, 5, 6, 9 and the amount 11. Does "biggest first" give the fewest coins?
    Answer

    No. Greedy takes \( 9 + 1 + 1 \): 3 coins. The best is \( 5 + 6 \): 2 coins.

  2. Meetings [1, 10], [2, 3], [4, 5], [6, 7]. How many does "earliest end" pick?
    Answer

    3: [2, 3], [4, 5], [6, 7]. The long meeting [1, 10] ends last and overlaps them all.

  3. In Twins the coins are 3 3 3. What is the answer?
    Answer

    2. One coin gives 3 against 6. Two coins give 6 against 3, which is strictly more.
