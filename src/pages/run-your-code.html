Input and output are only text

Your program does not see the problem page. It sees only text. The text it reads is the standard input (stdin). cin reads from it. The text it prints is the standard output (stdout). cout writes to it.

On Codeforces the judge puts the test into stdin. Then it compares your stdout with the right answer. So print only the answer, no extra words like "Enter n".

The command cin skips spaces and line breaks. So 3 and then a line 1 2 3 read exactly like 3 1 2 3. You never need to read a line break yourself.

The default way: Custom test on Codeforces

You need nothing on your computer. Codeforces has a page named Custom test. Inside a contest the same page is named Custom invocation. It runs your code on any input you give it.

  1. In the language list, choose GNU G++17, G++20 or G++23. Do the same when you submit.
  2. Paste your whole program into the big box for the code.
  3. Copy the sample input from the problem page. Paste it into the box named Input.
  4. Press Run. Read the box named Output. The page also shows the time and the memory your program used.

This is the default way. You install nothing, and the compiler is the same one the judge uses.

The local way: on your own computer

Later you may want to run code without the browser. This needs the compiler g++ on your computer. Save the code as a.cpp. Open a terminal in that folder.

g++ -std=c++17 -Wall a.cpp -o a
./a
./a < in.txt
LineWhat it does
1. CompileTurns a.cpp into a program named a. -std=c++17 picks the C++ version. -Wall prints warnings: hints about likely bugs.
2. RunOn Windows type .\a. The program starts and waits for input. Paste or type the input, then press Enter. The output appears under it.
3. Input from a fileReads the input from the file in.txt. You do not paste it again each time.

On Windows, use < in the Command Prompt (cmd): a < in.txt. PowerShell does not accept <. Some programs read "until the input ends". To end the input, press Ctrl+D (Linux, Mac), or Ctrl+Z and then Enter (Windows). Text printed with cerr also shows in the terminal, but the judge ignores it.

Test before every submit

  1. Every sample. Run every sample, not only the first. Copy the whole input, down to the last line.
  2. Compare letter by letter. YES is not Yes, and 3.0 is not 3. Look at every line of the expected output.
  3. Your own small tests. The samples are few and easy. Add three of your own:
    • the smallest input: \( n = 1 \), or the smallest value, like \( w = 1 \);
    • the biggest values: like \( w = 100 \), or a number \( 10^9 \);
    • all equal: like 5 5 5 5.
    Work out the right answer by hand first. Then run the test.

Read a compile error

A compile error means the code is not valid C++. Here a ; is missing after cin >> w. This is the real message of g++:

a.cpp:6:13: error: expected ';' before 'if'
    6 |     cin >> w
      |             ^
a.cpp:8:5: error: 'else' without a previous 'if'

a.cpp:6:13 means: file a.cpp, line 6, character 13. Fix only the first error, then compile again. The errors after it often come from the first one. Here the else error goes away when you add the ;.

The most common messages and their fixes are in the C++ reference, part "Reading errors".

Solve one together

Problem. Test the 4A program from the last lesson before you submit it. The sample input is 8. The expected output is YES.

  1. Open Custom test. Choose the language GNU G++17. Paste the whole program into the code box.
  2. The sample. Paste 8 into the Input box and press Run. The Output box shows YES. This matches the expected output. But one sample is not enough.
  3. Your own tests, by hand first.
    InputWhy this testRight answerProgram printed
    1the smallest \( w \)NONO
    2even, but 1 + 1 has odd partsNONO
    3oddNONO
    100the biggest \( w \)YESYES
    Every line matches.
  4. The trap test. Remove && w > 2 from the code and run the input 2 again. Now it prints YES, which is wrong. Your own small test found the bug before the judge did. Put the condition back.
  5. Submit. All tests match, so submit the code.

#include <bits/stdc++.h>
using namespace std;

void solve() {
    int w;
    cin >> w;
    if (w % 2 == 0 && w > 2) cout << "YES\n";   // even, and not 2
    else cout << "NO\n";
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int t = 1;
    while (t--) solve();
}

Wrong ideas people get

  • You may think: The code compiles, so it is correct.

    The truth: Compiling checks only the spelling, not the idea. Run the samples to test the idea.

  • You may think: I do not need to test the samples myself. The judge will tell me.

    The truth: In a contest a wrong submit costs you points or penalty minutes. Testing a sample takes 30 seconds.

  • You may think: My program prints nothing, so it is broken.

    The truth: Most often it waits for the rest of the input. Paste the whole input, then press Enter.

Common mistakes

  • You paste only the first line of the sample. The program waits for the rest.
  • You change the code but run the old program. On your computer, compile again after every change.
  • You test with your own input and trust the output. Work out the right answer by hand first.

Check yourself

  1. On your computer the program reads n = 3, then prints nothing and waits. What is the likely reason?
    Answer

    It waits for the 3 numbers. You pasted only the first line of the input. Paste the whole input.

  2. The compiler shows 5 errors. Which one do you fix first?
    Answer

    The first one. Then compile again: the other errors often came from it.

  3. Does cin read differently when 1 2 3 is on one line or on three lines?
    Answer

    No. cin skips spaces and line breaks, so both give the same three numbers.
